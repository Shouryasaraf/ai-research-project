# Broader live workload development protocol

Defined before executing this workload smoke series on 2026-10-08. This series is exploratory integration validation, not confirmatory testing or model selection.

- Families: steady, periodic bursts, gradual trend and flash crowd, as generated by `live_demand_schedule`. Training/calibration data are identical across families at a fixed seed; only future offered demand differs. The controller never sees the future schedule.
- Seed: 31. Policies: full proposed controller and reactive threshold. Three persistent flows, twelve one-second intervals, the same shaped topology as the original pilot. Eight trials total; all results retained. A single repetition per family cannot support uncertainty estimates or generalization.
- New implementation: durable route journal, readback, commit-time supported-state checks and conservative containment. Earlier pilot tables describe earlier code, not this revised controller.
- Primary descriptive outputs: paired goodput, application failures and commit count. Queue-drop counters are local observations, not end-to-end loss estimates. No policy/weight changes are allowed within this series.
- Each batch snapshots executed source/config files in addition to recording fingerprints. Summaries remain separate by family; do not pool duplicate policy/seed records across workloads.
- Stop on infrastructure failure; preserve failed/incomplete evidence and diagnose before any newly named rerun. No stopping based on performance. No tuning on these outcomes.

For a larger follow-up, first freeze a new protocol covering independent seeds, longer traces, flow-count mixtures and practical effect margins. Do not relabel this series as confirmatory.
